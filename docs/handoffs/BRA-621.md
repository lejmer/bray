## Observed generated code mismatch

The provider adapter reads a `ReportRecords` from `destination`, calls `admit_record_values(count, output, destination)`, destructures `(status, updated)`, writes `updated` back through `std.memory.write<ReportRecords>`, and returns `status`.

`ReportRecords` is a C-layout copy value containing three `usize` fields. On the verified x86-64 Linux target it occupies 24 bytes. The helper returns `(u32, ReportRecords)` in a 32-byte aggregate: status at offset 0 and records at aligned offset 8. The helper's generated code stores that aggregate.

The adapter instead reads `updated` as a 32-bit value at offset 4 and writes only 8 bytes to the destination. The expected operation extracts the 24-byte records value at offset 8 and writes all 24 bytes.

The observed instructions in `bray_runtime_report_records_admit` were:

```text
1c06aa: call helper at 1bd900 with result address rsp + 0xb0
1c06c1: movl 0xb0(%rsp), %eax
1c06c8: movl 0xb4(%rsp), %ecx
1c06cf: movq %rcx, (%rbx)
```

The helper symbol was `bray_instance_01ff30d15548be08597329e78d948facd7e4847cde6d3621e95efdd3d5643321`. The final abort was at `1d6a97`, offset `0x57` in `bray_instance_2d306927057231783869356bab72882943713a041f69d9a600f991d6659c7441`. Addresses describe this particular build.

These observations establish incorrect tuple extraction or writing across the generated adapter boundary. The responsible compiler stage remains unproven. Candidate boundaries include tuple projection in `crates/bray-lowering/src/lowering/projection.rs`, aggregate lowering in `crates/bray-lowering/src/lowering/expression/value.rs`, concrete type substitution, and generic memory-write realization.

Preserve the empty-chain invariant. Additional capacity, another admission path, or a fallback would hide the compiler defect.
